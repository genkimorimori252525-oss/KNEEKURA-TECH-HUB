# Start here: AI work across local and GitHub Tech Hub sources

This is a routing procedure, not a runtime authorization or feature acceptance.
Read it before selecting tools, interpreting historical search results, or launching
a Minecraft Water Tank.

## 1. Resolve the actual working source

When the coding environment exposes registered projects, find its KNEEKURA-TECH-HUB
checkout before assuming that a GitHub search is the entire available project.
Read that checkout's root README and AGENTS.md, if present. Inspect its current
branch/revision and dirty scope without resetting, pulling over, or discarding work.

Known local operational guide names are:

- `docs/PROJECT-GUIDE.md`: feature/tool routing, availability, selected worktrees,
  source references, authority boundaries, and the quality/speed workflow;
- `docs/TANK-OPERATING-GUIDE.md`: current Tank setup, source/world/profile matching,
  finite observation/camera controls, restoration and cleanup;
- `docs/AI-FEEDBACK.md`: known failures, corrections, scoped verification and gaps.

These files may be untracked local working documents. Their absence from GitHub
search is not proof that no guide exists. When present, read the project guide,
the relevant operating guide, and related feedback before using another source.
Do not upload their full contents or local runtime data merely to make them visible.

When a local guide is absent, report that absence and follow the tracked root README
and the applicable current department handoff. Never fabricate a missing guide.

## 2. Reconcile baseline and feature availability

The tracked [Minecraft current handoff](../departments/minecraft/CURRENT-HANDOFF-2026-10-02.md)
defines the main-line baseline and supersedes older documents that call themselves
current. Read the latest entry linked from the root README if this link changes.

Local guides can describe tools available only in a separate reviewed worktree or
unmerged feature branch. Confirm that exact source's branch/base, revision, command
help, build integration and acceptance limits before using it. Do not confuse guide
availability with installation, code presence with execution authority, or a later
document date with a combined accepted baseline.

## 3. Select the correct Tank

Current LAB source belongs to this repository's `departments/minecraft/lab/`.
Use the selected source's Debug Workspace / registered owner and disposable-world
contracts. Respect existing session, registry, finite lease, snapshot, process and
runtime-attestation gates. Record the selected source and runtime identities before
launch. Preserve explicit user STOP instructions independently of documentation.

The retained standalone KNEEKURA-LAB, old SimLab / Web Viewer, historical `runSim`
examples, and a locally listening Viewer are not evidence of the requested current
Tank. Do not launch or clone them as a fallback. They remain available as historical
evidence only. A browser rendering of retained samples does not prove native YSM
rendering or actual loaded MOD identity.

## 4. Retain discoveries without leaking local state

Record recurring routing failures and the limited result of a repair. Keep failed
receipts and historical claims. Write a public-safe decision record or PR summary
instead of publishing private paths, owner secrets, configurations, worlds or raw
conversation/log bundles. Missing, partial and unverified capabilities stay explicit.

For external product repositories, add a pointer to this routing procedure in their
own agent instructions: this repository's AGENTS.md cannot load automatically while
an agent works in another checkout.
