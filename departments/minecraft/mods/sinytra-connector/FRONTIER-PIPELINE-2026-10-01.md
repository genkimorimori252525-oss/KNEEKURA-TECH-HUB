# Connector FRONTIER pipeline and Launchpad integration

## Scope and result

This study follows Connector `c84a96a3c04aa4c5253032c338434de5329be08a` and its declared Launchpad `1.9.1+26.1.2` source at `a1d958c952f5ffd38daa8671354e9b8fdf30f9c9`. Connector declares `3.0.0-beta.6`, Minecraft `26.1.2`, NeoForge `26.1.2.95` and Java 25. These are immutable source declarations, not measurements of an installed pack or a resolved binary classpath.

The important architectural change from the Forge 1.20.1 ANCHOR is a division of work: **Connector selects and repairs foreign inputs; Launchpad supplies Fabric-convention metadata, nested-JAR, access and lifecycle integration into NeoForge.** The transformer is a separate project with service-loaded extensions and an injectable environment. It still relies on exact host code shapes and external Adapter/Loader/Mixin implementations. A smaller Connector patch table therefore does not prove that earlier compatibility obligations disappeared.

Unless a paragraph says **inference**, its statements describe the pinned source. All runtime, build, source-to-binary equivalence and actual patch-application results are **NOT_RUN / UNKNOWN**. No upstream wrapper, build, JAR, game, workflow or probe was executed. The companion JSON enumerates every acquired Connector and Launchpad path, independently checks byte size, SHA-256 and Git-blob SHA-1, and distinguishes fully read source from acquisition-only exclusions. A source-index status of PARTIAL is retained: complete scoped reading does not close the external dependency or binary boundary.

## Build and dependency boundaries

Connector's root project separates early service `main` code from game-facing `mod` code, embeds the latter as a Jar-in-Jar artifact, and shades the transformer, Adapter core, Class Tweaker and AutoRenamingTool into its full artifact. Adapter runtime is a separate Jar-in-Jar dependency. Service files are merged; duplicate non-service paths fail the full-jar task. The transformer has its own `runner` source set and shaded CLI artifact. This is phase/classloader packaging, not merely a directory organization. ## Admission and candidate selection

### Early reader and temporary stubs

Connector checks that the Launchpad API is available and that the expected `FabricModFactory.createModFile` signature is callable. Missing class or method disables its reader and locator; this check is not a full dependency-version or behavior validation. Reader priority is 500, ahead of the declared Launchpad reader priority 200. Its constructor installs logging/crash/context-classloader support and sends hidden IDs and aliases to the Loader fork. [Enable gate](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/util/ConnectorUtil.java#L53-L83), [reader startup](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorModFileReader.java#L42-L60)

The reader requires `fabric.mod.json`, rejects an explicit FMLModType manifest marker, and normally defers to native NeoForge TOML. A TOML `properties` entry named `connector:placeholder` makes the latter eligible; the implementation checks key presence, not its boolean value. It rejects upstream `fabric-api` / `fabric_api`, `mixinextras`, and metadata explicitly marked Launchpad-compatible. For remaining inputs it constructs a **stub** ModFile: no real ModInfo or language requirements, but parsed Fabric metadata remains available under `fabric:metadata`. This is an intermediate discovery object, not a loaded mod. [Eligibility and placeholder](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorModFileReader.java#L79-L141), [stub contract](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorModFileReader.java#L164-L245)

### Late locator and duplicate policy

The dependency locator declares lowest system priority and reflectively retrieves the pipeline's complete `loadedFiles` list. It initializes transformer plugins, separates stubs from host discoveries, applies the Fabric environment check and skips a candidate if its dash-to-underscore normalized ID already has a native non-library equivalent. For each Fabric ID it chooses highest Fabric Version, breaking ties toward shallower nesting. It then compares collisions with native library candidates using Maven artifact versions; if the Fabric candidate wins, expected native losers are exempted from split-package filtering. These are concrete selection rules, not ANCHOR's Fabric resolver/SAT graph algorithm transplanted unchanged. [Locator spine](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L56-L167), [selection](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L170-L270), [host-private access and names](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L304-L327)

After transformation, the locator prepares the failing-Mixin safeguard, computes module-safe JAR views, and hands them to Launchpad's `FabricModFactory.createModFile`. Non-generated candidates become MOD; generated libraries become GAMELIBRARY, or LIBRARY when the source's existing-library-parent condition applies. After offering converted results to the pipeline and recording their IDs/pending caches, it removes stubs; addModFile's boolean is not checked on this path. Successful factory construction is therefore distinct from confirmed host acceptance. The generated Adapter JAR is separately offered to the host discovery pipeline. [Host handoff](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L137-L167), [stub removal](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L70-L94), [type selection](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L272-L294)

## The complete Connector transformation path

### Input metadata and the two branches

`MetadataReader` parses Fabric metadata through the Loader fork. It starts from the current environment's declared Mixin configs, deliberately excludes configs declared only for another environment, and additionally scans conventional Mixin JSON filenames absent from the declared lists. A chosen config contributes its refmap, package and all class entries under `mixins`, `client` and `server`. Consequently, the resulting class-name set is an audit/discovery approximation, not a runtime-active-Mixin set. A jar is a generated library only when `fabric-loom:generated` is boolean true and `Fabric-Loom-Remap` is absent or not exactly `true`. [Metadata scan](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/jar/MetadataReader.java#L38-L163)

The generated-library branch registers only `FabricMetadataTransformer` then `JarSignatureStripper` and returns no audit trail. The ordinary branch reads local refmaps, creates a per-JAR PatchEnvironment and audit trail, gathers method patches and ordered ART transformers, runs the transformer chain, edits resulting Mixin configs/refmaps/services, silences audit failures from Mixin classes absent from discovered config class lists, and merges the remaining audit. Both branches tell ART to ignore `assets/` and `data/` paths. [Branch and orchestration](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/jar/JarTransformInstance.java#L48-L145)

**Version-specific observation:** the entire registered built-in chain at this revision contains no explicit intermediary-to-SRG/current-namespace remapper or ANCHOR-style AW-to-AT transformer. It uses named Minecraft owners/member strings and reads Class Tweaker resources with namespace `official`. ART's name and the variable `renameLibs` do not establish a renaming stage that the code does not register. This conclusion is scoped to these sources and built-ins; unknown third-party plugins may register additional transformations. [Built-in registration](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/plugin/BuiltinConnectorPlugin.java#L23-L47), [access-resource namespace](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/FieldToMethodTransformer.java#L24-L60)

### Plugin discovery is distinct from transformer ordering

`PluginManager` loads implementations with ServiceLoader once when initialized; the built-in provider is registered in a service descriptor. It asks every loaded plugin for method patches and JAR transformers separately for each ordinary JAR. A provider-construction `ServiceConfigurationError` is logged and that provider is omitted. The `TransformerPlugin.name()` contract says globally unique, but PluginManager does not enforce uniqueness of plugin names. The distinct transformer registration names are actually checked. [Plugin manager](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/plugin/PluginManager.java#L31-L89), [plugin API](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/api/TransformerPlugin.java#L8-L30)

Transformer registration makes a directed graph: a runs-before relation creates self→target; runs-after creates target→self. Absent optional targets and self-relations are ignored. Duplicate transformer names throw before sorting. The comparator supplied to host TopologicalSort is `OrderingHint` (EARLY, DEFAULT, LATE), then name; the exact external cycle failure behavior is not implemented in this source. An EARLY hint is a tie-break preference, not permission to violate an explicit edge. [Sorting algorithm call](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/plugin/TransformerRegistrarImpl.java#L52-L100), [ordering API](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/api/TransformerRegistrar.java#L11-L70)

The built-in declarations are:

| Transformer ID | Rule and work |
|---|---|
| `connector:analysis` | Before `connector:patches`; FieldToMethodTransformer, then ClassAnalysingTransformer inside one ClassNodeTransformer |
| `connector:mod_metadata` | DEFAULT hint; rewrites Fabric JSON and removes placeholder NeoForge TOML |
| `connector:signature_stripper` | DEFAULT hint; strips selected signature files and manifest metadata |
| `connector:patches` | LATE hint; Mixin/Adapter patcher inserted by JarTransformInstance before plugin registration |
| `connector:access_redirect` | After `connector:patches`; updates calls to renamed accessor/invoker methods |

**Inference:** with only these registrations and ordinary comparator-respecting topological selection, the intended built-in-only linear order is analysis → mod_metadata → signature_stripper → patches → access_redirect. The explicit invariant established directly by Connector is analysis before patches before access_redirect; external plugins add nodes/edges and may change the full order. Do not describe ServiceLoader encounter order as the transformer order.

Method-patch groups use a separate mechanism: stable descending numeric priority, then concatenation within each registered group. The built-in plugin registers three priority patches at 1000, four generated field-accessor patches at 500, and eight ordinary manual patches at 0. Equal-priority groups retain registration encounter order; therefore service discovery can still matter for equal-priority patch semantics. [Patch sorting](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/plugin/PatchRegistrarImpl.java#L16-L31), [built-in groups](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/plugin/BuiltinConnectorPlugin.java#L12-L27)

### Metadata and resource normalization

The metadata transformer changes dashes to underscores and adds `_nojpms` for a whole normalized ID equal to a reserved Java word. If the ID changes it retains the original ID in `provides`. It removes two specifically named primitive-string MixinExtras entrypoint values, rewrites missing known aliases in `depends` to the available target ID with wildcard `*`, strips numeric patch components from the `fabric-api` dependency's string predicate while preserving a `+` suffix, and writes `connector:active` and `launchpad:compatible` custom markers. It does not establish equivalence of the aliased APIs, normalize every possible dependency shape, or remove object-form entrypoint values. On metadata-processing exception it logs and returns the original entry; NeoForge TOML removal is a separate resource rule. [Metadata implementation](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/FabricMetadataTransformer.java#L17-L147), [alias lookup](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/DependencyConfiguration.java#L9-L18)

Signature stripping removes META-INF entries ending `.RSA` or `.SF`, clears manifest per-entry sections and removes Automatic-Module-Name. It is not a general signature-file classifier, signature verifier, or preservation of the upstream signature's trust meaning. [Implementation](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/JarSignatureStripper.java#L9-L33)

### Class and field adaptation

Four owner-qualified fields become getters: Biome climateSettings→getModifiedClimateSettings, Biome specialEffects→getModifiedSpecialEffects, Structure settings→getModifiedStructureSettings and FlowerPotBlock potted→getPotted. Reads match owner plus field name, not descriptor. GETFIELD and GETSTATIC are accepted by the predicate, but the replacement is always INVOKEVIRTUAL with `()` plus the original field descriptor. This is not a general safe conversion for arbitrary static fields. Matching owner/field access-widening entries are filtered out of the Class Tweaker resource; other Class Tweaker operations are forwarded. [Field transformations](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/FieldToMethodTransformer.java#L24-L135)

The accessor layer constructs one MethodPatch per replacement value, asks Adapter to target the class/field selector, converts matching Accessor annotations to Invoker annotations, prefixes method names with `connector$redirect$`, and records original name+descriptor by owner. A later pass redirects matching MethodInsn calls. Exact Adapter selector interpretation, class traversal timing and cross-JAR discovery guarantees are external/unverified. The shared plugin instance holds a ConcurrentHashMap; that data structure alone does not prove all required renames exist before every caller is visited. [Accessor generation and calls](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/AccessorRedirectTransformer.java#L16-L67), [annotation conversion](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/AccessorToInvokerTransformer.java#L16-L36)

ClassAnalysingTransformer rewrites two exact calls: Class.getResourceAsStream and NightConfig FileConfigBuilder.defaultResource to ConnectorMod static helpers that use the host mod-resource view. ClassNodeTransformer applies contained processors sequentially and only serializes changed classes, computing maxima and optionally frames. [Call rewrites](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/ClassAnalysingTransformer.java#L13-L39), [processor wrapper](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/ClassNodeTransformer.java#L11-L52)

### Mixin and non-Mixin paths

MixinPatchTransformer identifies Mixin classes from their invisible Mixin annotation, including classes omitted from existing config files, and sends them through Adapter's Patcher with DynamicPatches plus the gathered method patches. Its separate environment-stripper and field-type-usage list is applied in the **non-Mixin branch**, despite a broader nearby comment. EnvironmentStripper removes wrong-environment fields, methods, recursively referenced same-class lambda methods and environment-specific interfaces; it does not remove an entire class based on a class-level Environment annotation. [Actual branch](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/MixinPatchTransformer.java#L41-L58), [class processing](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/MixinPatchTransformer.java#L142-L194), [side stripping](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/EnvironmentStripperTransformer.java#L34-L141)

The BytecodeFixerUpper frontend supplies clean and dirty class lookups plus four declared type adapters: Holder.Reference→Object via value(), Identifier→String via toString(), ItemStack→Item via getItem(), and a no-instruction Mob→Monster adapter. It loads or saves a shared generated helper JAR with `FMLModType=GAMELIBRARY`. These registrations establish available adaptation strategies, not that each conversion is valid for every input. [BFU frontend](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/jar/BytecodeFixerUpperFrontend.java#L19-L58)

InheritingClassWriter attempts common-superclass resolution from the clean lookup first, then `Class.forName(..., false, contextLoader)` and ultimately ASM fallback. Thus the implementation aims to avoid initialization, but is not guaranteed to avoid class loading altogether. Generated Mixin extras use a plain ClassWriter with frames. Exact target hierarchy and classloader availability remain essential inputs. [Writer](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/InheritingClassWriter.java#L19-L84), [generated extras](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/MixinPatchTransformer.java#L171-L182)

### Refmaps and output finalization

RefmapStorage reads only the declared files present inside the input JAR; missing files warn and are skipped. SimpleRefmap merges with top-level `putAll`, so later maps replace a colliding class-level mappings map or environment-level data map rather than deeply merging every reference. The metadata refmap set is not a declared collision-precedence order. ConnectorRefmapHolder strips spaces for lookup, tries dot and slash class forms, falls back to the original reference, and copies mappings to generated classes while marking affected files dirty. [Storage and merge](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/RefmapStorage.java#L24-L51), [shallow merge](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/SimpleRefmap.java#L21-L27), [holder](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/patch/ConnectorRefmapHolder.java#L21-L56)

Finalization adds generated classes to the first matching config-package view, removes them from the pending generated map, and writes a dirty refmap only inside the generated-Mixin/config branch and only if its output file already exists. This is not an unconditional rewrite of every refmap. Package membership is tested with `startsWith`, so exact prefix-boundary assumptions matter. The final service sweep retains only provider lines whose class file exists in the same JAR, rewriting or deleting descriptors otherwise. It does not parse service comments or prove that an externally supplied provider is absent from the process. [Finalization](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/transform/MixinPatchTransformer.java#L60-L140)

## Class lookup cache audit and failure boundaries

The host environment retrieves clean Minecraft bytes for the physical side via Mojang launcher metadata when its cached clean JAR is unavailable. The source's HTTP helper does not explicitly check HTTP status or manifest checksums. This is a description of what the implementation would do; this study did not invoke it or acquire game binaries. The dirty lookup combines host libraries and every input candidate; optional early NeoForge coremod providers are applied to lookup bytes. Early-coremod failure logs and returns the original bytes, so an available dirty lookup is not itself proof that host patching succeeded. [Clean retrieval](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/util/GameCodeRetriever.java#L30-L107), [host environment](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/src/main/java/org/sinytra/connector/locator/ConnectorTransformerEnvironment.java#L79-L153), [early coremods](https://github.com/Sinytra/Connector/blob/c84a96a3c04aa4c5253032c338434de5329be08a/transformer/src/main/java/org/sinytra/connector/transformer/jar/EarlyCoremodTransformer.java#L37-L135)

Cache identity is environment cache-version plus SHA-256 of input bytes when an input exists. Production host cache-version is implementation-version plus physical dist; development uses `__dev__`; absent production version uses a random token. ## Launchpad metadata nested dependencies and access

Launchpad's regular reader is an author-opt-in route. Its factory requires Fabric JSON plus `custom.launchpad:compatible=true`, defers to ordinary NeoForge TOML except when the `launchpad:placeholder` key exists, and checks `loadsInEnvironment` **before creating the real ModFile**. Connector bypasses neither the factory nor this side check: it writes the compatible marker and supplies its transformed, filtered JAR. The factory uses a manifest-parser branch for explicit library types or generated metadata; other accepted inputs receive an in-memory NeoForge metadata representation. [Factory](https://github.com/Sinytra/Launchpad/blob/a1d958c952f5ffd38daa8671354e9b8fdf30f9c9/src/main/java/org/sinytra/launchpad/impl/FabricModFactoryImpl.java#L31-L82), [opt-in](https://github.com/Sinytra/Launchpad/blob/a1d958c952f5ffd38daa8671354e9b8fdf30f9c9/src/main/java/org/sinytra/launchpad/impl/FabricModMetadata.java#L81-L101)

Launchpad metadata processing first adds its active flag and a default FFAPI fluid-polyfill flag, normalizes dependency keys when enabled, applies top-level overrides, then normalizes the final mod ID and preserves its original spelling in `provides`. Overrides replace a whole top-level property; this is not a recursive merge. An overridden dependency object is not normalized again, and an overridden `custom` object can replace previously inserted flags. The host file-property active flag and Fabric custom-property marker are distinct channels. **Inference:** metadata consumers must track which stage and representation a flag belongs to instead of treating all flags as one global truth. [Preprocessing order](https://github.com/Sinytra/Launchpad/blob/a1d958c952f5ffd38daa8671354e9b8fdf30f9c9/src/main/java/org/sinytra/launchpad/impl/FabricModMetadata.java#L97-L155), [host properties](https://github.com/Sinytra/Launchpad/blob/a1d958c952f5ffd38daa8671354e9b8fdf30f9c9/src/main/java/org/sinytra/launchpad/impl/MetadataConverter.java#L47-L72), [runtime marker check](https://github.com/Sinytra/Launchpad/blob/a1d958c952f5ffd38daa8671354e9b8fdf30f9c9/src/main/java/org/sinytra/launchpad/impl/LaunchpadImpl.java#L39-L41)

VersionConverter converts intervals into Maven range fragments, inclusive equal endpoints into `[version]`, and missing/unbounded/empty-fragment inputs into `*`. Invalid Maven dependency specifications also fall back to `*` after logging. FML remains the resolver; translation is not evidence that all Fabric and Maven predicate semantics are equivalent. ## Reusable design conclusions and remaining unknowns

The following are **inferences for reuse**, not approved backports or runtime-certified techniques:

1. Separate admission, semantic repair, host representation and lifecycle execution. Keeping Fabric-convention support in Launchpad allows a native opt-in path and a repaired Connector path to converge on the same host factory without pretending both paths have the same input contract.
2. Specify two independent ordering systems. A before/after graph constrains whole-JAR processors; numeric priorities order Mixin patches inside one processor. Their identity, cycle, equal-priority and missing-target rules belong in the public extension contract.
3. Preserve original identity when adapting host identity. A normalized ID with an original-ID alias is traceable; wildcard aliases and reduced version predicates should never be treated as binary equivalence.
4. Treat class lookup, generated helpers and resource finalization as part of transformation. A successful instruction edit alone cannot establish valid frames, Mixin config reachability, service providers or module-safe package ownership.
5. Audit provenance belongs beside cache provenance. No audit, an ignored audit and a fresh passing audit are different observations. Cache keys should state which environment inputs they actually cover.
6. Transfer precise contracts, not names or patch counts. The four field replacements, fifteen built-in MethodPatches, registry timing interventions and host-private reflection are tied to this exact source/host generation. The [portability study](VERSION-PORTABILITY-2026-10-01.md) explains the separate ANCHOR redesign obligations.

Unresolved boundaries include the exact installed binary-to-source relation; resolved Loader/Adapter/ART/Mixin/NeoForge/JDK implementation closure; external plugin set and ordering outcomes; input-specific refmap collisions, generated classes, frame computation and cache invalidation; runtime entrypoint multiplicity/error recovery; real rendering/network/registry correctness; and all performance measurements. The finite source-reading batch can finish while these remain PARTIAL / UNKNOWN. Runtime execution is outside this task and is not proposed as a completion step.
