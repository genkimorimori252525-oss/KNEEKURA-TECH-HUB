# Connector ANCHOR: how a Fabric jar becomes a participant in a Forge game

Revision: `7f68ac02291fde986119a3f5cab85436bed5c350`, the supplied Minecraft 1.20.1 / Forge beta.50 anchor. This is a finite source study, not a successful game run, build, compatibility certification, or observation of resolved dependencies. Every mechanism below is a source declaration unless explicitly marked inference. The companion coverage ledger checks all 87 scoped paths: 20 non-transformer main Java files, 59 mod Java files, five mod resources, and three service descriptors. Its 86 text files were fully read (5,117 lines); the logo was visually inspected. File bytes match the acquired Git blob SHA-1 and SHA-256 inventory. Transformer Java/coremod JavaScript have a separate study; dependency implementation source is not silently included here.

## 1. The technical essence

Connector does not simply persuade Forge to accept the filename or translate Fabric API calls one by one. It constructs a hybrid loading environment with four coupled obligations:

1. **Admit the right artifacts.** Discover Fabric jars and their nested dependencies while respecting Forge's already-discovered mods, then run dependency/side selection before transformation.
2. **Make the artifacts acceptable to the host.** The transform pipeline supplies host-compatible code/resources; this host layer supplies normalized metadata and Java-module-safe views, so FML can accept them as mod files.
3. **Preserve the guest's initialization contract.** A Fabric Loader fork receives the final FML mod list, sets up Fabric entrypoints, and invokes preLaunch, main, and the physical-side initializer at deliberately early host hooks.
4. **Reconcile mismatched runtime invariants.** Forge freezes registries, wraps values, changes field types, routes rendering and item interactions differently, and exposes different event/API surfaces. Connector selectively restores expected insertion points, views and timing; FFAPI and other external implementations remain essential dependencies.

The coordinating spine is `locateFabricMods`: discovery → nested graph → duplicate policy → dependency resolution → `JarTransformer.transform` → split-package handling → synthesized Forge ModFiles. Later, `ConnectorEarlyLoader` and `ConnectorLoader` perform the distinct Fabric initialization duties. [Locator spine](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L92-L158), [Fabric setup](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorEarlyLoader.java#L90-L141), [entrypoint dispatch](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/ConnectorLoader.java#L32-L57)

## 2. Artifact admission: preserve the graph before choosing what executes

### Service/bootstrap wiring

Three service descriptors expose `ConnectorLoaderService` to ModLauncher, `ConnectorEarlyLocator` as a Forge mod locator, and `ConnectorLocator` as a dependency locator. The early locator reflectively moves Connector's dependency locator to the end of the list, so it can see Forge's discoveries first. It also locates Connector's embedded mod jar through manifest attributes and the `jij:` filesystem. This is source-level integration with host discovery, not an independent Fabric process. [early locator](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorEarlyLocator.java#L25-L52), [embedded jar lookup](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/EmbeddedDependencies.java#L34-L99)

`ConnectorLoaderService.onLoad` replaces the launch-plugin ordering: Mixin first, a lenient Forge enum extender next, Connector's plugin after that, then the remaining plugins. `initialize` wraps `ImmediateWindowProvider.updateModuleReads`: when no prior error is present it calls loader setup, loads an empty `DummyTarget` to initialize Mixin plugins before sensitive classes, then calls preLaunch. Its declared `ITransformer` list is empty; this does not mean no transformation happens, because bulk transformation is invoked by the dependency locator and the injected launch plugin also mutates access flags. [service callbacks](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/ConnectorLoaderService.java#L52-L133), [prelaunch plugin](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/ConnectorPreLaunchPlugin.java#L25-L60)

The exact outer order in which ModLauncher/FML calls those callbacks is a host-implementation boundary. Inside each callback the call order above is directly visible.

### Discovery and nested jars

Roots come from the mods directory, development-only classpath discovery, and optional comma-separated additional locations (directories contribute their immediate entries). Mods-directory and additional-location roots are filtered by `.jar`, excluded transformer locations and Fabric metadata. Development classpath discovery instead excludes claimed legacy-classpath entries and requires an existing non-directory artifact with Fabric metadata. A normal `META-INF/mods.toml` makes a jar a Forge candidate rather than a Connector candidate; a special placeholder property allows a combined jar through. Placeholder Forge mod versions are set to `0.0` to favor the Fabric candidate in FML duplicate resolution. [root preparation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L95-L124), [discovery predicates](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L161-L255)

Declared nested jars are extracted recursively into the Connector temporary area, using cached copy operations. A parent-to-child multimap is carried into Fabric's candidate graph; nested candidate paths are null while root candidates receive paths, and child parent links are added. Missing declared nested files are filtered out at extraction, so a missing required dependency must surface through later resolution rather than through an unconditional extraction exception. [nested extraction](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L258-L282), [candidate construction](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/DependencyResolver.java#L103-L120)

### Duplicate and dependency policy

Already-loaded non-library Forge mod IDs are excluded early. Upstream `fabric_api` is deliberately excluded to prevent conflicts with Forgified Fabric API, including unported leftover modules. Library-ID collisions get a version comparison: when the Fabric version is highest, older Forge-library candidates are put on an ignored-package-filtering list in anticipation of FML's own deduplication; otherwise Connector's candidate is removed. This is not a general proof that all duplicate libraries are interchangeable. Fabric-vs-Fabric candidate selection is ultimately delegated to the resolver, despite the duplicate-handler's broad comment. [explicit exclusions](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/ConnectorUtil.java#L39-L56), [duplicate policy](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L285-L322)

The resolver sees Fabric candidates, Forge mods wrapped as Fabric builtins, Java and the embedded Fabric Loader version. Global aliases allow known Forge ports with different mod IDs to satisfy Fabric dependencies. The code deliberately widens aliased dependency version constraints to `*`, drops aliased `BREAKS` constraints, and removes `fabricloader` dependency constraints when no earlier alias match applies. A configured alias is handled first, so its wildcard/BREAKS policy can take precedence. These are compatibility policies, not evidence that the relaxed requirements are truly satisfied at binary/runtime level. The underlying solver is a Fabric Loader-fork implementation boundary. [resolver and constraint adaptation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/DependencyResolver.java#L52-L100), [builtins](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/DependencyResolver.java#L123-L154)

### Why side filtering is late

The anchor does not reject wrong-side roots during `shouldIgnoreMod`. Instead, after `ModResolver.resolve`, the inverse candidate map selects Connector jars and `loadsInEnvironment` removes wrong-side jars from the transformation set. Therefore nested jars remain discoverable before final side admission. This ordering is a concrete repaired design, not arbitrary placement. [discovery before resolution](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L126-L142), [ignore predicate](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorLocator.java#L319-L322), [post-resolution side filter](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/DependencyResolver.java#L66-L75)

The already-traced history explains it: PR #926 moved side rejection into early discovery to address wrong-side loading; #991 reported that this suppressed Yttr's nested dependencies; the maintainer attributed that regression to #926. Commit `96cdbd49a2fb1ef81657f40431f7a59e7b18dcbd` moved environment filtering after resolution, and this anchor retains it. The symptom/causal attribution is historical author reporting; the changed predicate and ordering are direct code evidence. No controlled runtime reproduction was performed in this study. [Earlier repair](https://github.com/Sinytra/Connector/commit/4b2014653be008e2f6463226f0224c1d1144c087), [maintainer attribution](https://github.com/Sinytra/Connector/issues/991#issuecomment-2043604217), [later repair](https://github.com/Sinytra/Connector/commit/96cdbd49a2fb1ef81657f40431f7a59e7b18dcbd)

**Reusable lesson, bounded to container-based loaders:** discovery/graph construction and execution eligibility are different phases. Excluding a container must not automatically erase dependencies other eligible components may require. This does not imply every descendant of an excluded container must execute.

## 3. Metadata and the dual mod identity

`ConnectorLoaderModMetadata` retains the Fabric metadata object while normalizing the host-facing ID: hyphens become underscores, Java reserved words receive `_nojpms`, and the original ID is added to `provides` when changed. The Forge-facing version removes `+`; versions not beginning with a digit are omitted so FML can supply its default. Side, jars, language adapters, mixin configuration and custom values are otherwise delegated. Redundant MixinExtras bootstrap entrypoints are filtered for the specified newer version threshold to avoid duplicate class definition. [normalization](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorLoaderModMetadata.java#L26-L98), [identity aliases](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorLoaderModMetadata.java#L121-L148), [MixinExtras filtering](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/ConnectorUtil.java#L194-L200)

`ConnectorModMetadataParser` constructs an **in-memory** NightConfig and `ModFileInfo`, not a standalone TOML conversion file. It chooses `javafml` or `lowcodefml`, attaches both original metadata and the `connector_transformed` property, fills descriptive/license/icon/contact/custom fields, and selects side-specific display tests. It does not recreate all Fabric dependency edges as Forge TOML dependencies; Fabric resolution already happened. [metadata adaptation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ConnectorModMetadataParser.java#L37-L116)

Later, the accepted `LoadingModList` is fed to `FabricLoaderImpl.addFmlMods`. Connector-marked mods are recorded and always included. `hiddenMods` can hide other host mods from that Fabric-facing view; it is not a disk-level mod-disable switch. The real relationship is one host process with a Forge-facing container identity and a Fabric-facing API/entrypoint view. [accepted-list propagation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorEarlyLoader.java#L99-L112)

## 4. Lifecycle: emulate the guest's timing, not just its method names

The launch plugin installs provider inheritance fixes, seeds the Fabric mod list, decorates Mixin configs and adjusts Fabric ASM resource lookup. The wrapped module-read callback separately calls `FabricLoaderImpl.setup`, the dummy-class trigger and `preLaunch`. `FabricLoaderImpl.setup` and language-adapter instantiation are dependencies whose internals were not captured here. [launch initialization](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/ConnectorPreLaunchPlugin.java#L25-L35), [setup/preLaunch hook](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/ConnectorLoaderService.java#L53-L70)

`ConnectorLoader.load` invokes `main`, then `client` or `server` according to physical `FMLEnvironment.dist`. The client hook is inside `Minecraft` construction; the dedicated-server hook precedes `ServerModLoader.load`; datagen hooks before `gatherAndInitializeMods`. This keeps Fabric initialization early enough for its direct registry/modification expectations. It does not translate every Fabric lifecycle event into a Forge event. [dispatch](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/ConnectorLoader.java#L32-L57), [client hook](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/boot/MinecraftMixin.java#L11-L17), [server hook](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/boot/ServerMainMixin.java#L10-L15), [datagen hook](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/boot/DatagenModLoaderMixin.java#L10-L15)

Errors are staged for Forge's error presentation during setup/discovery, with a shared prior-error check preventing many downstream actions. This is not a blanket transactional boundary: the entrypoint loader throws before `LazyEntityAttributes.release` on failure, and `finishedLoading` is a flag, not a reentry guard. The wrapped callback also does not recheck errors between its setup/dummy/preLaunch calls. These observations limit what a successful return or stored flag proves; they are not a reproduced failure report. [error storage](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorEarlyLoader.java#L53-L81), [setup error behavior](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/loader/ConnectorEarlyLoader.java#L120-L140), [load completion state](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/ConnectorLoader.java#L32-L57)

### Registry timing is the most invasive semantic bridge

Early vanilla snapshot and inner built-in freeze calls are suppressed. Before Fabric entrypoints finish, `ForgeRegistry.getDelegateOrThrow` can return an existing holder or construct an intrusive one before normal host registration has supplied it. Later client/dedicated-server run hooks call `GameData.vanillaSnapshot` and immediately unfreeze built-in registries; `preventFreeze` becomes true, after which `MappedRegistry.freeze` is bypassed. The NamespacedWrapper frozen-field assignment is separately suppressed. Calling this simply “registration support” hides a significant host-invariant change. [snapshot delay](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/BootstrapMixin.java#L24-L29), [freeze suppression](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/BuiltInRegistriesMixin.java#L9-L14), [early holder creation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/ForgeRegistryMixin.java#L16-L33), [unfreeze state](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/ConnectorMod.java#L95-L105), [client snapshot](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/MinecraftMixin.java#L19-L24), [server snapshot](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/MinecraftServerMixin.java#L20-L25), [wrapper suppression](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/registries/NamespacedWrapperMixin.java#L9-L15)

Four Forge attributes receive placeholders during Fabric initialization, then are released. When the object-builder API module is present, a Forge attribute event replaces placeholder keys in vanilla and Forge attribute suppliers. A separate ForgeHooks patch combines event-added attributes with a vanilla supplier changed by a mixin. This is a targeted timing reconciliation for entity metadata, not a generic entity/AI port. [attribute staging](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/compat/LazyEntityAttributes.java#L25-L79), [conditional listener](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/ConnectorMod.java#L47-L58), [attribute merging](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/ForgeHooksMixin.java#L32-L43)

## 5. Classloader and Java-module boundaries

Transformed jars cannot simply share packages as on a flat classpath. `SplitPackageMerger` builds package ownership, gives an owner a union view of the same package from other Fabric jars, excludes that package from the donors, and filters packages already claimed by Forge/BOOT/SERVICE. Mod metadata records remain distinct; this is package-view surgery rather than shading every library. The separate Forge filter removes Connector-owned packages from eligible Forge jar union filesystems, then invalidates cached package discovery. Root/META-INF resources are treated differently from class-bearing package paths. [package ownership](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/SplitPackageMerger.java#L38-L134), [union views](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/SplitPackageMerger.java#L144-L172), [host package filter](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/ForgeModPackageFilter.java#L19-L69), [filter exceptions](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/PackageTracker.java#L25-L38)

Other boundary fixes are deliberately specific:

- `authlib` is made transformable by disabling its BOOT module reader/package set and exposing the original provider as `connector$authlib` in GAME. This does not migrate already-loaded Class objects. Trusted lookup comes from Unsafe and depends on JDK and SecureJar internals. [module migration](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/hacks/ModuleLayerMigrator.java#L28-L79)
- GAME's ModuleClassLoader is associated recursively with parent layers so service implementations can be found without normal parent-loader delegation; the source itself limits bootstrap/platform provider coverage. [service inheritance workaround](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/hacks/ServiceProviderInheritanceWorkaround.java#L38-L87)
- Newly created ForkJoin workers inherit the creator's context classloader; default and common-pool factories are replaced. Existing workers are not shown being retrofitted. [context-loader propagation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/hacks/ConnectorForkJoinThreadFactory.java#L22-L40)
- Every non-private Minecraft field and method is widened to public after mixin processing, addressing access failures when remapping moves consumers across packages. This does not widen private members or all classes. [access reconciliation](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/ConnectorPreLaunchPlugin.java#L37-L60)
- Fabric ASM gets a GAME SecureJar for two generated mixin packages, generated URL-root lookup, name flattening and sealed-enum permitted-subclass support. For `mm`/`mm_shedaniel`, the Minecraft module reader falls back to generated resources. This is support for concrete generated-class conventions, not arbitrary classloader emulation. [generation hooks](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/FabricASMFixer.java#L32-L95), [providers](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/service/FabricASMFixer.java#L117-L177)

## 6. Runtime intervention map: what each gameplay facet really means here

### Rendering, particles and data-shape views

Forge changes color maps from numeric-ID containers into holder-keyed maps, and particle providers into resource-location keyed maps. Connector adds getters returning live facades with the original expected shapes: numeric IDs are translated through registries on access, and writes hit the same backing Forge map. This preserves shared state instead of making a stale copy. The bytecode-rewrite origin is in the companion transformer study. [block colors](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/fieldtypes/BlockColorsMixin.java#L18-L37), [item colors](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/fieldtypes/ItemColorsMixin.java#L18-L37), [particle providers](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/mixin/fieldtypes/ParticleEngineMixin.java#L16-L35), [live mapper](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/compat/fieldtypes/RedirectingIdMapper.java#L12-L61)

The compatibility surface is incomplete: the particle integer map's entry-set, key-set and values views explicitly throw; its default-return-value field is stored but `get(int)` uses ordinary `Map.get`. Treat it as a supported-operation adapter, not a full `Int2ObjectMap` implementation. [partial map contract](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/java/org/sinytra/connector/mod/compat/fieldtypes/RedirectingInt2ObjectMap.java#L51-L98)

Client setup rebuilds render-type layer IDs, permits later block-render-type registration, and load completion fills missing sign/hanging-sign/banner/pot materials. These adapt lifecycle/data assumptions; they do not implement a replacement renderer. ## 7. Cache validity: exact inputs, not a promise of all environmental equivalence

The shared cache stamp contains Connector's package implementation version and physical distribution, plus SHA-256 of the input bytes when an input exists. A matching stamp is accepted only if the output exists. A mismatch removes output/stamp; a missing stamp removes an orphan output. The action runs before the new stamp is saved. `connector.cache.enabled` defaults true and only literal `true` enables it when set. If the package version is unavailable, a memoized random five-letter value prevents normal cross-process reuse. [cache check and write](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/ConnectorUtil.java#L122-L172), [stamp persistence](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/ConnectorUtil.java#L208-L231), [version and side](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/main/java/org/sinytra/connector/locator/EmbeddedDependencies.java#L52-L60)

Inference: this invalidation rule is reproducible for those explicit inputs, but does not independently fingerprint every Forge library, coremod, config or dependency graph change. Output naming and additional transformer caches have their own rules in the companion pipeline study. A source-level matching hash is not a runtime proof of transformation correctness.

## 8. What is truly not applicable, and what remains unknown

For this compatibility layer, a catalogue of its own new mobs, blocks, crafting recipes, combat mechanics, quests or terrain generators is **not applicable to the scoped implementation**: it is adapting other mods' behavior rather than authoring such content. The inspected resources contain metadata, mixin/access-transformer declarations and branding, not a new gameplay content pack. But registry, interaction, AI, worldgen, network, UI and recipe-book facets are **applicable and mapped above**. They must not be marked absent just because Connector is infrastructure.

The following remain **external/unverified**, not “not applicable”: full FFAPI event/API behavior; Fabric Loader-fork resolver, language adapters and mapping resolver; Adapter's patch selection/rewrites; Forge/Mixin/ModLauncher target implementations; resolved runtime classpaths; concrete mod combinations; host/client/server/datagen execution success; cross-network interoperability and long-running cache behavior. Declaration of a target or required mixin does not prove it applied successfully. The mixin JSON itself requires Java 17, declares common/client/server partitions and sets default injection requirement 1. [declared mixin set](https://github.com/Sinytra/Connector/blob/7f68ac02291fde986119a3f5cab85436bed5c350/src/mod/resources/connectormod.mixins.json#L1-L57)

## 9. Reusable architecture lessons, with limits

1. **Preserve identities and graph structure across admission stages.** Keep original metadata while manufacturing host metadata; discover nested dependencies before final eligibility. This applies when one artifact can contain independently useful components, not automatically to every package manager.
2. **Treat lifecycle as an API surface.** Registration windows and freeze/snapshot timing can matter as much as symbol names. Connector's approach changes host invariants substantially; copying the unfreeze strategy into another loader without understanding its registry contracts would be unsafe.
3. **Prefer shared-state views when bridging field shapes.** Color and particle adapters translate keys against a single backing map. But enumerate which collection operations are really supported; a nominal interface implementation can hide unsupported operations.
4. **Create explicit synthetic hook surfaces where host control flow diverges.** HUD/use-on scaffolds let transformed mixins retain meaningful entrypoints and cancellation. This requires a paired rewrite plus runtime host hook; an empty method by itself does nothing.
5. **Module ownership and generated-class visibility are first-class concerns.** Relocation is not always viable when reflection and string names matter. Union views, module providers and service lookup can substitute, at the cost of host/JDK-version coupling.
6. **Distinguish recovery policy from semantic correctness.** Wildcard aliases, missing-texture fallback, tag guesses and empty resources may make a path usable without reproducing every original behavior. Record these approximations explicitly.
7. **Keep source declaration, dependency implementation, historical reports and runtime verification separate.** The side-filter history offers a concrete ordering lesson; the stale postApply guard offers a static inconsistency; neither substitutes for a launch test.

The coverage ledger links every scoped path to its byte hash, line ranges, role, facet tags, and the boundary on its interpretation. It is a complete path review for this finite scope, not a claim that all external behavior or every possible runtime branch has been proven.
