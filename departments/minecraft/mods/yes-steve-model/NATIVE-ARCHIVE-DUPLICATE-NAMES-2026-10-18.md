# Duplicate-name policy in the integrity manifest

## Result
The integrity tree is **first-wins for equal produced name bytes and length**. Each later retained record is still read and hashed before duplicate detection, but its newly allocated node is freed without replacing the original hash, adding a second equal node, or issuing a duplicate-specific error. This is first in the reader-vector order, not necessarily first in physical archive storage order.

The audited reader-vector construction layer appends eligible records without comparing their names against earlier records. It does not deduplicate or reject names. **Whether all lower-level archive parser paths accept duplicate entries remains unresolved**: this is not a whole-parser audit. The later builtin loop processes the original vector in its original order, independently of the unique-name integrity tree. Conditional duplicate records therefore remain candidates for separate later read/write calls; final filesystem overwrite behavior is not established here.

## Exact insertion and ordering evidence
- `3d891c..3d8933` obtains begin/end from the reader's record vector; `3d895a` advances by `0x48`. Existing prefix exclusions apply before reading (`3d896c..3d89b6`). For identical names the same prefix decision applies.
- Every retained record is read at `3d89ea` and hashed at `3d8a0c`, before allocating its candidate `0x38`-byte node at `3d8a24..29`. Node `+0x20` is name length, `+0x28` its pointer and `+0x30` the computed hash (`3d8a2e..3e`). The name is borrowed from stable reader-vector storage; this block does not replace the record itself.
- Descent compares candidate/current names through imported `memcmp` for the smaller length (`3d8a9a..3d8abe`); a common prefix is ordered by the length difference (`3d8a60..86`). The implementation clamps the signed 64-bit difference to signed-int extrema. For valid string lengths this gives shorter-prefix-first lexicographic order. The memcmp result is tested by sign; there is no case folding, locale collation, path normalization or basename-only comparison here. Equal keys require equal bytes and equal length. High-bit bytes follow memcmp's unsigned-byte comparison semantics, not signed-char alphabetic order.
- Negative comparison descends left `node+0x10`; nonnegative descends right `+0x18` (`3d8a86..8d`). At the insertion boundary, predecessor selection (`2ba670`, called at `3d8af1`) and reverse comparison at `3d8b0c..57` require an existing predecessor to be strictly less than the candidate. Equality gives EAX=0 and `3d8b64` jumps to `3d8940`, which deallocates **only the candidate node** (`3d8945..4d`), then advances the vector at `3d895a`.
- Only accepted insertions call the link/rebalance helper `2ba6d0` at `3d8bf2` and increment unique node count at `3d8bf7`. The helper manipulates color/parent/left/right links; the equal-key rejection occurs before it. No store replaces an existing node's `+0x30` hash on the duplicate branch.
- Manifest traversal starts at the tree leftmost node and uses successor `2ba620` (right subtree then its leftmost descendant, otherwise parent ascent). Existing `hash-manifest-format-contract` documents its serialization. Thus output is one entry per unique produced name, ordered lexicographically, with the first retained record's hash. Hash equality is not the duplicate criterion. Later duplicate read/hash errors can still abort before their nodes are discarded.

## Reader-vector boundary, audited separately
`4dab30` stores caller mode byte at reader `+0x50` (`4dab9d`) and calls `4d8cb0`; this init caller supplies mode **0** (`3d8895`). Within the vector-building region `4d9a9c..4da37b`:
- A vector holder is allocated and installed at reader `+0x18` (`4d9aa7..4d9ae9`). The earlier constructor leaves this pointer null, so the construction path is selected.
- Header parser `4e2b00` is invoked initially at `4d9c04`, with second argument zero. The bounded helper window confirms central-directory signature `0x02014b50` selection for that mode (`4e2bc9..bd6`), but does not establish every validation or rejection path.
- `4d9d1a..1f` skips vector append when parser field `+0x30 <= 0`. The positive field is copied to record `+0x40` (`4da10a` or `4da132`) and later used as the requested output length. Without a full parser-field audit, this report does not upgrade that to a universal statement about ZIP empty files/directories.
- Names originate at parser `+0x58`. Mode 0 follows `4d9d88`, computes `strlen` (`4d9d99`) and copies that C-string range to owned vector storage. The optional per-byte conversion loop `4d9e0a..1e` is only the mode-1 path and is not selected here. Thus the tree receives these produced C-string names; it is not proven to compare every byte of the raw archive filename. In particular, the producer length is strlen-derived, although this does not establish whether embedded NUL names can pass lower layers.
- Spare-capacity append writes fields into vector end and advances end by `0x48` (`4d9f60..4da10e`). Reallocation constructs the new record at the old end offset, copies older records in their existing order (`4da15b..4da1dd`), and updates begin/end/capacity (`4da241..256`). No prior-name lookup, equality test, set insertion or duplicate rejection occurs in these append paths.
- Iteration advances a directory cursor by `0x2e +` three parsed 16-bit lengths (`4da27d..2a5`), seeks there, and invokes `4e2b00` again (`4da35c`). This establishes enumeration order at this layer. Alternate initialization/recovery/header validation paths and the remainder of `4e2b00` are not fully audited, so it is not a proof that arbitrary duplicate-bearing archives are accepted.

## Relationship to later builtin processing
`3d97b1..bc` reopens begin/end of the **same reader vector**, not the integrity tree. `3d97f0` advances every candidate by `0x48`; the builtin-prefix test and blacklist full-match filtering precede read `3d98d9` and write call `3d99ce`. There is no lookup back into the unique-name integrity tree or duplicate tracking in this loop.

Record-directed reader `4dad30` loads each record's `+0x08` cursor (`4dad6d`), range-checks it, installs it as reader cursor, seeks (`4dae3c`) and reparses its header (`4dae5c`). It does not begin with a name-based find that would select the first tree entry. If duplicate records exist, pass all filters, and preceding stages succeed, they can therefore lead to multiple separate ordered calls using their own metadata cursors. Whether writes replace existing contents, fail, or alias after normalization/filesystem resolution is outside this seam. No exploitability or safe extraction conclusion follows.
