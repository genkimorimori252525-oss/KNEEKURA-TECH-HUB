## Pending-nextAnim caveat and rejected counterexample

A concrete out-of-scope counterexample to “missing selection is always absent” is: select valid A without processing, then select missing B, then process. The first selection stores A at P4:97. The second calls resetToIdle but returns at P4:75 without replacing or clearing A. P18 then consumes A. This is an API/lifecycle counterexample, not an observed runtime failure, and not by itself a mixed-subtype counterexample. It is already excluded by the original report's explicit pending-null/direct-repeated-selection caveat.

C.process's transition loop is NOT evidence that this sequence occurs in the ordinary controller path. Its back-edge 71→53 is reached only with holder count==0 (64–68). C.transition computes new count at 301–332, resets removed holders with full reset at 414, stores new count at 425, and performs selection only for indices below that count (431–555). Thus a zero-count pass selects no holders and clears removed pending selections; a nonzero-count pass stops that transition loop before processing. An initial suspicion that this loop defeated the consumed-pending premise was checked and rejected. No ordinary built-in controller counterexample was established. The proof remains intentionally conditional rather than claiming coverage of arbitrary calls, hierarchy/state changes or callbacks.

## Boundaries to retain

Do not promote this result to runtime/native transition provenance, malformed-input safety, numerical blending equivalence, arbitrary public writers, concurrent/reentrant execution, or all callers' visitation ordering. “Unchanged state” must cover the transition supplied to each player and the segment list contents during clone creation; stable per-player length alone does not imply equal lengths across players. No interpolation/clock-cohort equivalence is newly certified. Runtime remains untested and its separate blocker is unchanged.
